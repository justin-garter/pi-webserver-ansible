## 1. Architecture

```
Internet
   |
   v
Cloudflare (proxy: justingarter.com, www — DDoS, CDN, TLS termination at edge)
   |
   v
RT-AX88U Pro (AiMesh primary, VLAN/SDN controller)
   |  port forwards: 80/tcp, 443/tcp, 51820/udp -> 192.168.54.180
   |
   +-- Main LAN                                 192.168.50.0/24
   +-- CABJJ Wireless-Guest (VLAN 52)           isolated
   +-- CABJJ Wireless-IoT   (VLAN 53)           isolated
   +-- CABJJ Wired-DMZ      (VLAN 54)           192.168.54.0/24
          |
          +-- LAN1 (Access, VLAN 54) --> Pi 5 1GB       192.168.54.180   ACTIVE, 1000Mb/s
          +-- LAN2 (Access, VLAN 54) --> (empty — was the 8GB, decommissioned Aug 9)
          +--      (Access, VLAN 54) --> minecraftserver 192.168.54.10    admin via this host
```

**Design principle:** the server is single-homed on the DMZ. WiFi and Bluetooth are disabled at the firmware layer, not just unconfigured — a dual-homed host bridges the two networks regardless of firewall rules.

### Verified isolation (August 9, 2026)

| Direction | Result | How verified |
|---|---|---|
| DMZ → Main LAN | **blocked** | `ping 192.168.50.1` from the Pi times out |
| Main LAN → DMZ | **blocked** | `Test-NetConnection 192.168.54.180 -Port 2222` from workstation fails |
| Internet → DMZ | 80/tcp, 443/tcp, 51820/udp only | router forward table |

**This corrects runbook v1 §1**, which claimed Main LAN → DMZ was open on 2222. It is not, in either direction.

**Consequence: WireGuard is the only management path.** There is no LAN-side fallback. If the tunnel fails, recovery is physical console access.

### Network management — read before changing anything

**NetworkManager owns the network. netplan is NM's *storage backend*, not a separate system.** The files in `/etc/netplan/90-NM-<uuid>.yaml` are generated by NM. Configure with `nmcli`. Never hand-edit those YAML files and never run `netplan apply` — you will fight the renderer.

```bash
# correct way to change addressing
sudo nmcli connection modify netplan-eth0 ipv4.addresses 192.168.54.180/24 ...
sudo nmcli connection up netplan-eth0
```

Static config lives in `/etc/netplan/90-NM-75a1216a-9d1a-30cd-8aca-ace5526ec021.yaml` (eth0).

### cloud-init — disabled

Raspberry Pi OS trixie uses cloud-init to apply Imager's first-boot customization. It is **disabled** via `/etc/cloud/cloud-init.disabled`.

Reasons: it rewrote `/etc/hosts` on every boot from `manage_etc_hosts: true`; it was already degraded (missing `cc_netplan_nm_patch` module); and it would contend with Ansible over hostname, hosts, and network config.

Re-enable by deleting that flag file. Existing NM connections persist independently.

**`/boot/firmware/user-data` and `network-config` were deleted.** They contained the account's yescrypt password hash and the WiFi PSK in cleartext. `/boot/firmware` is FAT32 — its `-rwxr-xr-x root root` is fabricated at mount time and enforces nothing.

### Radios disabled

`/boot/firmware/config.txt`:
```
# DMZ host: single-homed on eth0, no radios
dtoverlay=disable-wifi
dtoverlay=disable-bt
```

Firmware-level, survives NetworkManager and package updates.

Two behaviors worth preserving if this is ever rewritten:

- It reads each record's existing `proxied` flag from the API before writing, rather than hardcoding. Hardcoding silently breaks the proxied/unproxied split on the next IP change.

## 6. Firewall — nftables

`/etc/nftables.conf`, enabled via `systemctl enable nftables`. Hand-written, not ufw.

```nft
table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;
        ct state established,related accept
        ct state invalid drop
        iif lo accept
        ip  protocol icmp   icmp   type { echo-request, destination-unreachable, time-exceeded } accept
        ip6 nexthdr  icmpv6 icmpv6 type { echo-request, nd-neighbor-solicit, nd-neighbor-advert,
                                          nd-router-advert, packet-too-big,
                                          destination-unreachable, time-exceeded } accept
        tcp dport { 80, 443 } accept
        udp dport 51820 accept comment "wireguard"
        iifname "wg0" tcp dport 2222 accept comment "ssh — wireguard only"
        counter comment "dropped"
    }
    chain forward {
        type filter hook forward priority 0; policy drop;
        ct state established,related accept
        iifname "wg0" ip daddr 192.168.50.0/24 drop comment "VPN must never reach the LAN"
        iifname "wg0" oifname "eth0" ip saddr 10.10.10.0/24 ip daddr 192.168.54.10 \
            tcp dport 22 ct state new accept comment "VPN admin -> minecraftserver SSH"
        counter comment "forward dropped"
    }
    chain output  { type filter hook output  priority 0; policy accept; }
}
```

### Scoped table replacement — not `flush ruleset`

The file opens with `table inet filter` / `delete table inet filter` rather than `flush ruleset`. **This matters.** fail2ban maintains its own `inet f2b-table`, and `flush ruleset` deletes every table on the host — so a playbook run would silently wipe fail2ban's active bans while fail2ban continued reporting them as enforced. The bare declaration creates the table if absent so the delete cannot fail on a fresh host, and `nft -f` applies the whole file as one atomic transaction, so there is no window where the host is unfirewalled.

After any ruleset change, confirm fail2ban's table survived:

```bash
sudo nft list tables    # expect BOTH inet filter and inet f2b-table
```

### Routed access through the tunnel (added Aug 13, 2026)

This host terminates the WireGuard tunnel and now also routes **one** narrowly-scoped flow to `minecraftserver` (`192.168.54.10:22`), rather than standing up a second VPN endpoint or forwarding another WAN port. Peers already carried `AllowedIPs` for the whole DMZ `/24`, so no client config changed.

Requires `net.ipv4.ip_forward = 1`, set via `/etc/sysctl.d/99-wg-forward.conf`. Both the sysctl and the firewall rules are driven from the same `nft_forward_allow` list in Ansible, so they cannot drift apart — an empty list sets forwarding back to `0`.

Three deliberate choices:

- **The rules live in the existing `forward` base chain.** nftables traverses *every* base chain on a hook, so a second chain would still be filtered by the original's `policy drop` — presenting as intermittent failure rather than an obvious error.
- **Tunnel → trusted LAN is explicitly dropped** ahead of any accept. The router's VLAN already blocks it; stating it here makes the intent auditable on the one host that could otherwise become a pivot into the LAN.
- **No masquerade or SNAT.** The destination sees the real `10.10.10.x` source, so its logs attribute connections to a specific peer instead of blaming this host for everything.

Verification:

```bash
sysctl net.ipv4.ip_forward                 # expect 1
sudo nft list chain inet filter forward    # expect the rules above, in order
# from a VPN client:
ssh justin@192.168.54.10                   # should succeed
ping -c2 -W2 192.168.50.1                  # must time out
nmap -Pn -p 80,443 192.168.54.10           # must find nothing
# on minecraftserver — confirms no NAT:
ss -tnp | grep :22                         # expect source 10.10.10.x
```

**ICMPv6 is enumerated by type rather than blanket-accepted.** NDP needs specific types; nothing else has to get through.

**UDP 443 (HTTP/3) is deliberately absent.** It is not in the router's forward list, and Cloudflare reaches origin over TCP. Caddy is configured not to advertise `h3` to match — see §7c.

SSH is reachable **only** over the WireGuard interface. There is no LAN-side fallback (§1), so a broken tunnel means physical access to the host. No monitor is attached and there is no serial console fitted — see `docs/recovery.md` before you need it, not after.

### Changing the ruleset remotely

Always arm a dead-man switch first:

```bash
sudo systemd-run --on-active=300 --unit=fw-rollback nft flush ruleset
sudo nft -f /etc/nftables.conf
# open a SECOND session and confirm it works
sudo systemctl stop fw-rollback.timer
```

## 7. Services

### 7a. SSH

**`/etc/ssh/sshd_config.d/00-hardening.conf`** (600 root:root) — the authoritative config:

```
Port 2222
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
```

**Why a `00-` prefixed drop-in.** `/etc/ssh/sshd_config` has `Include /etc/ssh/sshd_config.d/*.conf` at **line 12**, and sshd takes the **first value obtained** for most keywords — not the last. Drop-ins are read in lexical order, so `00-` beats cloud-init's `50-cloud-init.conf`, and anything written further down the main config is dead text.

This is precisely how v1 §7a's "PasswordAuthentication no" was false in production for months.

**`ssh.socket` is disabled on Debian**, so `Port` in config works normally. This is *not* the Ubuntu 24.04 behavior documented in v1 §7a — no socket override is needed here.

Verify effective config, never the file:
```bash
sudo sshd -T | grep -iE '^port|permitrootlogin|passwordauthentication|kbdinteractive'
```

Verify *behavior*, not just config:
```bash
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -p 2222 justin@<host>
# want: Permission denied (publickey), with no password prompt
```

### 7b. fail2ban

Version **1.1.0-8 from Debian apt**. The manual `.deb` install from v1 §7b is not needed — trixie ships 1.1.x, so the Python 3.12 `asynchat` breakage is gone.

**Critical: `banaction` must be nftables.** This host has no `iptables` binary. `jail.local` came from a ufw host and shipped `iptables-multiport`, which would have made every jail *look* healthy while banning nothing.

```
banaction = nftables[type=multiport]
banaction_allports = nftables[type=allports]
ignoreip = 127.0.0.1/8 ::1 10.10.10.0/24
```

`10.10.10.0/24` is in `ignoreip` because it's the only management path — a self-ban there is a physical trip.

Requires `python3-systemd` for the sshd jail's journal backend.

**Active jails:**

| Jail | Port | Source |
|---|---|---|
| `sshd` | 2222 | systemd journal, `_SYSTEMD_UNIT=ssh.service` |
| `caddy-404` | http,https | `/var/log/caddy/access.log`, maxretry 10 / findtime 120s / bantime 3600s |

Filter at `/etc/fail2ban/filter.d/caddy-404.conf`:
```ini
[Definition]
failregex = ^.*"client_ip":"<HOST>".*"status":404.*$
```

**The caddy-404 jail is worthless unless `trusted_proxies` is correct** (§7c). If Caddy logs Cloudflare's edge IP as `client_ip`, fail2ban bans Cloudflare.

fail2ban creates its own `table inet f2b-table` with a chain at priority `filter - 1`, evaluated before the main filter table. The two coexist; do not try to merge them.

**`f2b-table` does not exist on a freshly booted host with zero bans.** The table, set, and chain are created lazily at the *first ban*, not at service start. So `nft list ruleset` on a clean boot shows no `f2b-table` while `fail2ban-client status` reports both jails active — which looks exactly like the failure mode from the `flush ruleset` bug (§6) but is normal behavior. Confirmed Aug 14, 2026 after a reboot. Do not diff a freshly booted ruleset against a snapshot taken from a long-uptime host and conclude fail2ban is broken.

To distinguish "not created yet" from "genuinely broken," force a ban and watch the table appear:

```bash
sudo fail2ban-client set caddy-404 banip 198.51.100.42   # TEST-NET-2, safe
sudo nft list tables                                      # f2b-table should now exist
sudo fail2ban-client set caddy-404 unbanip 198.51.100.42
```

Verify a ban actually lands in the ruleset:
```bash
sudo fail2ban-client set sshd banip 203.0.113.55   # TEST-NET-3, safe
sudo nft list ruleset | grep -A10 f2b
sudo fail2ban-client set sshd unbanip 203.0.113.55
```

### 7c. Caddy

Version **2.11.4**, official Cloudsmith repo (not Debian's).

**Config:** `/etc/caddy/Caddyfile`
**Web root:** `/var/www/portfolio`
**Cert store:** `/var/lib/caddy/.local/share/caddy` — migrated from the 8GB host, `chown -R caddy:caddy`. Migrating it kept ACME out of the cutover path entirely.

Global block:
```
{
    servers {
        protocols h1 h2
        trusted_proxies static <Cloudflare IPv4 ranges>
    }
}
```

**`trusted_proxies` is security-critical, not cosmetic.** Without it every access-log entry records a Cloudflare edge IP instead of the visitor, which breaks fail2ban. With it correctly scoped, spoofed `CF-Connecting-IP` / `X-Forwarded-For` headers from untrusted sources are ignored.

Verified by sending forged headers from a non-Cloudflare address and confirming `client_ip` reflected the real source. Verified in production: `remote_ip` shows a Cloudflare edge, `client_ip` shows the actual visitor.

**The IP list is static and dated July 2026.** Cloudflare changes ranges. See §11.

**`protocols h1 h2`** stops advertising `alt-svc: h3` — the firewall drops UDP 443, so advertising HTTP/3 only causes clients to attempt QUIC, fail, and fall back.

**Security headers:** HSTS (1yr, includeSubDomains, preload), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (geolocation/microphone/camera disabled), `-Server`.

Note the auto-HTTPS redirect vhost on port 80 still emits `Server: Caddy`; the `-Server` directive only applies to the site block. Cloudflare overwrites it downstream.

**Access log:** JSON to `/var/log/caddy/access.log`. Not enabled by default — requires an explicit `log` block.

**systemd override** `/etc/systemd/system/caddy.service.d/override.conf`:
```ini
[Service]
LogsDirectory=caddy
LogsDirectoryMode=0750
ReadWritePaths=/var/log/caddy
Environment="GOMEMLIMIT=256MiB"
MemoryMax=384M
```

`GOMEMLIMIT` is a soft GC target — Caddy otherwise infers ~890MB from total RAM, which is most of the box. `MemoryMax` is the cgroup hard ceiling: kill Caddy rather than let it drag a 1GB host into swap thrash.

> **Trap:** never run `sudo caddy validate` or `sudo caddy run`. Doing so creates `/var/log/caddy/access.log` owned `root:root`, after which the service (running as `caddy`) cannot open it and fails to start with a misleading `permission denied`. Fix: `chown caddy:caddy /var/log/caddy/access.log`.

**TLS:** automatic via Let's Encrypt HTTP-01. Renewal path is live now that 80/443 forward here.

**Known gaps:** no rate limiting, no WAF. Static HTML with no forms or server-side logic, so the attack surface is small. Revisit if the site gains dynamic content.

### 7d. WireGuard

**This is the only management path into the DMZ.**

- Interface `wg0`, `/etc/wireguard/wg0.conf` (600 root:root)
- Address `10.10.10.1/24`, listen `51820/udp`
- Server keypair rotated Aug 11, 2026 after being printed by an `ansible-playbook --diff` run.
  Read the current public key with `sudo wg show wg0 public-key`.
- One peer, the Windows workstation, AllowedIPs `10.10.10.2/32`. Peers are declared in
  `group_vars` and asserted by the wireguard role.
- No `PostUp`/`PostDown` rules — nothing iptables-specific to translate
- `systemctl enable wg-quick@wg0`

**The keypair was originally migrated verbatim from the 8GB host rather than regenerated**, which is why the Windows client required zero changes at cutover. It was rotated on Aug 11 after being printed by `ansible-playbook --diff`; the playbook now carries `no_log: true` on any task that renders a secret.

### Rotating the server keypair

The rotation breaks the only connection to the host, by design. Make both ends revertible first.

1. Generate on the control node: `NEW_PRIV=$(wg genkey); echo "$NEW_PRIV" | wg pubkey`
2. In WireGuard for Windows, duplicate the tunnel and set the copy's `[Peer] PublicKey` to the new public key. Keep the original — it is the rollback.
3. On the host, back up and arm a timed revert:
   ```bash
   sudo cp /etc/wireguard/wg0.conf /etc/wireguard/wg0.conf.bak
   sudo systemd-run --on-active=300 --unit=wg-rollback /bin/bash -c \
     'cp /etc/wireguard/wg0.conf.bak /etc/wireguard/wg0.conf && wg syncconf wg0 <(wg-quick strip wg0)'
   ```
4. Edit `PrivateKey` with `nano` (not `sed` — keeps the key out of shell history), then `sudo bash -c 'wg syncconf wg0 <(wg-quick strip wg0)'`. The session dies here.
5. Switch tunnels in Windows. On reconnect, `systemctl stop wg-rollback.timer` and delete the backup.
6. **Update the Ansible vault**, then verify the vault and the host agree:
   ```bash
   ansible-vault view group_vars/webserver/vault.yml --ask-vault-pass \
     | awk -F': ' '/^wg_private_key/{gsub(/"/,"",$2); print $2}' | wg pubkey
   ssh WebServer 'sudo wg show wg0 public-key'
   ```
   These must match. Skipping step 6 leaves the playbook holding the old key, and the next apply writes it back and locks you out.

**Client (Windows):** address `10.10.10.2/32`, endpoint `vpn.justingarter.com:51820`, AllowedIPs `10.10.10.0/24, 192.168.54.0/24`, PersistentKeepalive 25.

The tunnel terminates on this host. Since Aug 13 2026 it also routes one narrowly-scoped flow onward to another DMZ host — see §6 and `nft_forward_allow`. Peers already carry `AllowedIPs` covering the whole DMZ `/24`, so a permitted destination is reachable directly from a VPN client with no jump host:

```
ssh justin@192.168.54.10
```

`forward` policy remains `drop`; only flows listed in `nft_forward_allow` pass, and `net.ipv4.ip_forward` is driven off the same variable so the sysctl and the ruleset cannot disagree. An empty list turns routing off entirely.

If you need a destination that is *not* in the allow list, jump through this host rather than widening the rule:

```
ssh -J justin@192.168.54.180:2222 -p 2222 justin@<destination>
```

Note the syntax: `host:port` works only inside `-J`; the destination needs `-p`.

## 9. Thermal Monitoring

**Script:** `/usr/local/bin/pi-thermal.sh`
**Units:** `pi-thermal.service` + `pi-thermal.timer` (hourly, `OnBootSec=2min`, `Persistent=true`)
**Log:** `/var/log/pi-thermal.log`

```
2026-08-08T22:55:16-04:00 temp=45.0'C throttled=0x0 load=0.04 0.03 0.00
```

### Decoding `get_throttled`

Bits 0–3 are **current** state; bits 16–19 are **sticky since last boot**. A nonzero value does not mean "throttling right now."

| Bit | Meaning |
|---|---|
| 0 | under-voltage detected |
| 1 | ARM frequency capped |
| 2 | currently throttled |
| 3 | soft temperature limit active |
| 16 | under-voltage **has occurred** |
| 17 | ARM frequency capping **has occurred** |
| 18 | throttling **has occurred** |
| 19 | soft temperature limit **has occurred** |

`0xe0000` = bits 17, 18, 19 — everything happened at some point, nothing active. **Only a reboot clears the sticky bits.** Expect the hourly log to keep reporting the last high-water mark until then.

### Observed

| Condition | Temp | Throttled |
|---|---|---|
| Idle, production traffic | 43–46°C | `0x0` |
| 17% CPU (100 Mb-bound load) | 60.9°C | `0x0` |
| Saturated, 11.6k req/s | **84.5°C** | `0xe0008` — soft limit, frequency capping, and hard throttling all triggered |
| Idle — **after Active Cooler**, Aug 14 | 34.0°C | `0x0` |
| Saturated, 12.0k req/s — **after Active Cooler**, Aug 14 | **64.2°C** | `0x0` — nothing triggered |

**Active Cooler installed August 14, 2026**, alongside the N04 NVMe adapter and a new case. Peak under sustained synthetic load fell 20.3°C, from 84.5°C to 64.2°C, with no throttle bit set at any point in the run.

Fan curve as observed: stopped below ~50°C, 1,605 RPM at 52.1°C, stepping to ~4,363 RPM at 60.9°C, peaking near 5,445 RPM. It continues ramping for 30–60s after load ends — RPM keeps climbing while temperature falls. That is hysteresis in the firmware curve, not a fault.

Reading `fan1_input` as 0 at idle is expected and is **not** evidence the fan is dead or unplugged. The only way to confirm the fan works is to drive the SoC past ~50°C and watch RPM go nonzero:

```bash
cat /sys/devices/platform/cooling_fan/hwmon/hwmon*/fan1_input
```

Context for honesty in any writeup: **the production workload does not need it.** This box idles in the mid-40s under real traffic, and a static site behind Cloudflare will never approach the load that caused this. What the cooler buys is the ability to sustain full CPU without frequency capping, which matters the moment this host does anything CPU-heavy, and costs $5 to remove as a variable permanently.

Temperature, not RAM, is the binding constraint on this hardware. Memory never came close to mattering (§10).

## 10. Performance Baseline

### Current — August 11, 2026

`wrk` on the host itself against loopback, after the gigabit link was restored. No external client was available, so the load generator shares four cores with Caddy — **these numbers are a floor, not a ceiling.**

Requires a temporary `127.0.0.1 justingarter.com` line in `/etc/hosts`, otherwise `wrk` sends SNI `127.0.0.1`, Caddy has no cert for it, and every connection fails at handshake. Remove the line afterward.

wrk -t2 -c50 -d30s --latency
  Requests/sec:  11669.23      Transfer/sec:  127.54MB
  p50 4.38ms   p75 10.50ms   p90 19.13ms   p99 42.40ms

### Two failure modes that cost two wasted runs — read before benchmarking

Both produced *misleading* output rather than obvious errors.

**1. Never benchmark plain HTTP on :80.** Caddy answers with a 308 redirect carrying `Connection: close`, so `wrk` opens a fresh TCP connection per request instead of reusing 100. At ~11k/s each connection leaves a conntrack entry in TIME_WAIT, exhausting the table in under a second.

**`nf_conntrack_max` on this host is 8192.** Once full, the kernel drops new SYNs *before* nftables evaluates them — so the input chain's `dropped` counter stays at 0, `wrk` reports no socket errors, and the summary shows a healthy per-thread `Req/Sec` beside a total two orders of magnitude too low. The only direct evidence is `dmesg`:

```bash
sudo dmesg -T | grep -i conntrack | tail -3
cat /proc/sys/net/netfilter/nf_conntrack_count /proc/sys/net/netfilter/nf_conntrack_max
```

8192 is fine for real Cloudflare-proxied traffic and has never been approached in production. It is only a ceiling under connection-churning synthetic load. Do not raise it to make a bad test pass — fix the test.

**2. The `/etc/hosts` line is mandatory, not optional.** Documented above and ignored on Aug 14, costing a full failed run: `wrk -H 'Host: ...' https://127.0.0.1/` sets the HTTP header but **not** SNI. Caddy has no cert for `127.0.0.1`, every handshake fails, and the result is 0 requests with tens of thousands of connect errors — which reads like a server fault and is a client misconfiguration.

**Always validate one request before spending 120 seconds measuring a million:**

```bash
curl -s -o /dev/null -w 'status=%{http_code} bytes=%{size_download}\n' https://justingarter.com/
# want: status=200 bytes=11241 — anything else, stop and fix before benchmarking
```

Watch `nf_conntrack_count` during any run. Steady near the connection count means keep-alive is working; climbing into the thousands means you are churning connections and the numbers are worthless.

## 11. Status and accepted tradeoffs

### Resolved

1. ~~**eth0 links at 100 Mb/s.**~~ **RESOLVED Aug 10 2026 — it was the patch cable.** Isolated by testing the original cable on LAN1, where it also capped at 100. LAN2's run is fine; the cable had a damaged or missing pair.

   Worth recording because the diagnostic evidence was misleading. On LAN2 the link partner advertised only `10baseT`/`100baseT` with no `1000baseT`, which normally points at the far end — capability bits ride in FLP bursts over pair 1-2, which even a two-pair cable carries, so a bad cable *should* still show the partner advertising gigabit. It didn't. Auto-negotiation on a degraded cable is less clean than the theory suggests. **Swap the cable first regardless of what `ethtool` implies about the partner.**

2. ~~**SSH open to the whole DMZ segment.**~~ **RESOLVED Aug 11 2026.** Now `iifname "wg0" tcp dport 2222 accept`. WireGuard became a hard dependency with no fallback as a result.

3. ~~**No active cooling.**~~ **RESOLVED Aug 14 2026** — Active Cooler fitted with the N04 NVMe adapter and a new case. Peak under sustained load 84.5°C → 64.2°C, no throttle bits set. See §9.

4. ~~**Not codified as Ansible.**~~ **RESOLVED Aug 11 2026** — [github.com/justin-garter/pi-webserver-ansible](https://github.com/justin-garter/pi-webserver-ansible). Eight roles, vaulted secrets, idempotent across consecutive runs.

5. ~~**Playbook never proven against bare metal.**~~ **TESTED Aug 16 2026.** The NVMe was wiped and the host rebuilt from the playbook alone, then diffed against a pre-wipe manifest.

   Result: every one of the 192 files the playbook manages came back with no difference in content, ownership, or permissions, and the `inet filter` ruleset was byte-identical. Within its scope it reproduces the host exactly.

   Outside that scope it is not a bare-metal build — it configures a host that is already reachable, and five prerequisites have to be established by hand first. Full procedure in `docs/rebuild-from-scratch.md`.

### Accepted tradeoffs

Deliberate, revisited when the thing that justified them changes.

- **No rate limiting or WAF.** Static HTML with no forms and no server-side logic. Revisit if the site gains dynamic content.
- **Caddy is pinned out of unattended-upgrades** (§7e), so Caddy updates are a scheduled manual task rather than an automatic one.
- **No external uptime monitoring.** The site going down is an inconvenience, not an incident.
- **`trusted_proxies` is a static list** (§7c) rather than a scripted refresh. Refresh procedure in `docs/making-changes.md`; it is checked whenever visitor IPs are reviewed.
- **IPv6 Cloudflare ranges are absent**, because the origin publishes no AAAA record and Cloudflare therefore connects over IPv4. They go in before an AAAA record does, not after.
- **WireGuard is the sole management path**, trading a convenient fallback for taking a listening SSH port off the segment entirely. The cost is real and has been paid — see `docs/recovery.md`.
- **`base` reports leftover Wi-Fi connection profiles rather than deleting them**, since removing the profile you are connected through is not something a playbook should do unprompted.

### Open

- **No serial console.** `BOOT_UART=1` is already set in the EEPROM, so a USB-to-TTL adapter on three GPIO pins would give console access from the desk. Without it, any recovery beyond a power cycle requires physically opening the case.

### Cutover / rollback

When a second host exists, cutover is performed entirely at the router by repointing the port forwards. Neither host's IP changes, both run the full service stack simultaneously, and only the one receiving forwarded traffic is live.

Move the **tunnel first** (`51820/udp`), verify management access, then move the service (`80`, `443`). Management should follow the production box.

Router admin is on the trusted LAN and does not depend on the tunnel, so rollback is always possible and takes under a minute with no shell access.

The 8GB predecessor was decommissioned Aug 9 2026, so there is currently no standby to cut over to. Recovery is via `docs/recovery.md` instead.
